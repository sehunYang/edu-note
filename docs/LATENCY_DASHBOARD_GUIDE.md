# 지연 개선 — 대시보드 작업 지침 (사용자 수행)

코드로 배포된 지연 개선(①' getClaims 폴백, ③ 연결 유지, ④ 스켈레톤/라우터 캐시)과 별개로,
아래 **두 가지는 대시보드에서만 할 수 있는 작업**입니다. 각각 10분 내외이며 순서 무관,
따로따로 해도 됩니다. 문제가 생기면 각 섹션 끝의 롤백을 따르세요.

> 배경 계획서: `.omc/plans/qc-v1-latency-fix-plan.md`, `.omc/plans/qc-v1-latency-followup-guide.md`

## A. 트랜잭션 풀러 전환 (P2) — `DATABASE_URL` 포트 5432 → 6543

**효과**: 서버리스 인스턴스가 여럿일 때 DB 연결 획득이 빨라지고, 유휴 연결이 Postgres
백엔드를 점유하지 않아 idle_timeout 10분(③)과 궁합이 좋습니다.

**안전 근거(이미 확인됨)**: 앱의 모든 postgres.js 클라이언트가 `prepare: false`
(트랜잭션 풀러 필수 조건)이고, 트랜잭션 사용처 4곳은 단일 `db.transaction()` 블록이라
트랜잭션 모드에서 안전합니다. 세션 기능(LISTEN/NOTIFY, 세션 변수)은 쓰지 않습니다.

### 단계

1. **새 URL 확인**
   Supabase 대시보드 → 프로젝트 → 상단 **Connect** 버튼 → **Transaction pooler** 탭.
   URL이 아래처럼 포트만 다른지 확인합니다(호스트 동일):
   ```
   postgresql://postgres.ntdvgneiqzeopmlevuwj:[비밀번호]@aws-1-ap-northeast-2.pooler.supabase.com:6543/postgres
   ```

2. **Vercel 환경변수 변경**
   Vercel 대시보드 → 프로젝트(edu-note) → **Settings → Environment Variables** →
   `DATABASE_URL` 편집 → 값에서 `:5432` 를 `:6543` 으로만 바꿔 저장 (Production 환경).
   `PUBLIC_DATABASE_URL` 이 따로 있다면 동일하게 변경합니다.

3. **재배포**
   env 변경은 재배포해야 반영됩니다: **Deployments → 최신 배포 → ⋯ → Redeploy**.

4. **스모크 테스트 (5분)**
   - 로그인 → 홈 대시보드 정상 로드
   - 세팅실 → 학생 명단 조회 + 아무 학생 속성 1건 수정 → 저장 확인
   - 공지실 → 할 일 1건 추가 → 삭제
   - 학생 공개 링크 1개 열어 정상 렌더 확인
   - (선택) 상담 슬롯 예약/취소 1회 — 트랜잭션 경로 확인

5. **로컬도 동일하게** (선택, 로컬 개발 속도용)
   `.env.local` 의 `DATABASE_URL` 포트도 `:6543` 으로 변경.
   이후 통합 테스트 1회: 기존 테스트 커맨드 그대로 (`RUN_DB_ITEST=1 npx vitest run`).

### 롤백

Vercel env 의 포트를 `:5432` 로 되돌리고 Redeploy. (데이터 변경 없음 — 연결 방식만 차이)

## B. JWT 서명 키 마이그레이션 — getClaims 로컬 검증 활성화 (① 본안)

**효과**: 코드에는 이미 `getClaims()` 가 배포되어 있습니다. 지금은 프로젝트가 legacy
대칭 키(HS256)라 **Auth 서버 검증으로 폴백** 중이며(기존과 동일 속도), 비대칭 키로
전환하는 순간부터 모든 요청의 인증이 **네트워크 왕복 없이 로컬 검증**됩니다.
상호작용당 100~250ms 고정 오버헤드가 사라지는 가장 큰 레버입니다.

**트레이드오프(수용됨)**: 로컬 검증은 토큰 강제 폐기(로그아웃/밴)가 토큰 만료 시까지
(최대 1시간) 반영되지 않습니다. 단일 사용자 allowlist 앱이라 실질 영향 없음.

### 단계

1. Supabase 대시보드 → 프로젝트 → **Project Settings → JWT Keys**
   (메뉴명이 "JWT Signing Keys" 또는 "Auth → Signing Keys" 일 수 있음 — 2025년 도입된
   새 서명 키 UI).

2. **Migrate to new signing keys** (또는 "Start using new signing key") 클릭.
   - 새 비대칭 키(기본 ECC P-256) 생성을 선택합니다.
   - 마이그레이션은 2단계입니다: (1) 새 키를 *standby* 로 추가 → (2) **Rotate** 로
     새 키를 현재 서명 키로 승격. 대시보드 안내를 따르세요.
   - 기존 로그인 세션은 유지됩니다: 이전 키는 JWKS 에 남아 기존 토큰 검증에 계속
     쓰이고, 토큰 갱신 시점부터 새 키로 서명됩니다.

3. **확인 (전환 직후)**
   - 앱 새로고침 → 로그아웃되지 않고 정상 사용 가능해야 함
   - 시크릿 창에서 새로 로그인 1회 → 정상
   - 학생 공개 링크(/p/…)도 1개 열어 확인 (인증 무관 경로지만 회귀 확인)

4. **legacy 키 폐기 (선택, 1주 후 권장)**
   모든 토큰이 자연 갱신된 뒤(액세스 토큰 만료 1시간) 대시보드에서 이전 키를
   **Revoke** 하면 마이그레이션 완료. 급하지 않습니다.

### 확인 방법 (로컬 검증이 실제로 켜졌는지)

전환 후 페이지 이동/버튼 반응이 눈에 띄게 빨라지는 것이 1차 신호입니다.
정량 확인을 원하면: 아무 페이지에서 개발자도구 Network → 서버액션 POST 의 응답시간을
전환 전/후 5회씩 비교(워밍업 1회 제외). 100ms 이상 단축이 기대치입니다.

### 롤백

새 키 전환 후 문제가 생기면 대시보드의 키 목록에서 이전 키를 다시 현재 키로 rotate.
코드 롤백은 불필요합니다 — `getClaims()` 는 어떤 키 구성에서도 동작합니다(폴백 내장).
